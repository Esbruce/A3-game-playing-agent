4a. In my implementation, alpha-beta cutoffs are detected in two places in the minimax method. The first is the main move loop. After each child is searched, I update alpha if it is the maximising player's turn (X), or beta if it is the minimising player's turn (O). Alpha is the best score the maximiser can already guarantee on the path so far, and beta is the best score the minimiser can already guarantee. If alpha >= beta, the player above would never let the game reach this node, so the remaining siblings cannot change the result. I break out of the loop and add one to alpha_beta_cutoffs_this_turn. The second is the transposition table, which is only used when both use_zobrist_hashing and pruning are True. Before expanding a node, I hash the position and look it up. An entry is only used if it was searched at least as deep as I need now. If the entry is EXACT, I return its value straight away without searching. If it is a LOWER or UPPER bound (stored when an earlier search was pruned), I use it to tighten the window by raising alpha or lowering beta. If that closes the window (alpha >= beta), I return immediately. This is counted as a useful hit. If there is no usable table entry, or hashing is off, the node is searched normally. When depth_remaining reaches 0, or there are no blank squares left, I call the static evaluation (or the autograder's special_static_eval_fn when one is supplied). The static evaluation only supplies leaf scores. The pruning decision is always made by comparing alpha and beta.

The saving grows with depth, which is what I expected (the unpruned tree grows by about a factor of 6-8 per ply but alpha-beta grows much more slowly). At depth 4 from the empty board it cut 127 times.

4c. Alpha is the best score that MAX can already force somewhere above on the current path, and beta is the best score MIN can already force. Consider a MAX node it has a minimum value that can be garunteed by expanding moves via it the current max. As opening more nodes will only ever result in the node taking a larger score. Now look at a MIN node that is a child, it is the parent of some other MAX nodes. Now if we open the first of those child MAX nodes and it has a smaller score than the minimum that the grandad MAX already garuntees, then there is no point looking at the other grandchild nodes. As the largest the MIN will take is already smaller than the MIN garunteed already by grandad MAX. The min case is the mirror image. What makes this safe is that alpha only ever goes up and beta only ever goes down, so a window that has closed (alpha >= beta) stays closed for everything below it. The returned value for a pruned node might be only a bound rather than its true minimax value, but the bound is on the correct side of the cutoff so the root value and the root move are exactly the same as plain minimax. This is why I got the same move with and without pruning every time. Because I only replace the best move on a strictly better score, ties go to the first move in both versions as well.

5a. static_eval looks at every window of k squares in a row (horizontal, vertical and both diagonals) that fits on the board. A window containing a forbidden square '-' is dead, and a window with both an X and an O in it is contested, so both are worth nothing. Every other window is counted by how many marks its owner has in it, giving x_windows[n] and o_windows[n]. The score is the sum for n = 1 to k-1 of 10^(n-1) * (x_windows[n] - o_windows[n]), so positive is good for X and negative is good for O. The intuition is that each live window is a line that could still become a win, and one extra mark makes it ten times more valuable, so a window one move from completion matters much more than a few weak ones. If a window is completed the function returns +/- 10^(k+1), which is more than any unfinished position can score for any k. Inside minimax I also treat a completed line as a terminal leaf and add or subtract depth_remaining, so quicker wins score higher and slower losses score less badly.

5b. This is from Randy vs ALI-G tic-tac-toe game (Randy-vs-ALI-G-in-TTT-round-1). X had played (0,1) and (0,2), ALI-G (O) had played the centre, and it was O's turn:

  . | X | X
 ---+---+---
  . | O | .
 ---+---+---
  . | . | .

Observing the X only windows of 3 tiles: row 0 has 2 X's and no O (worth 10), column 2 has 1 X and no O (worth 1) Observing the O only windows of 3 tiles: row 1 has 0 X's and 1 O (worth -1), diagonal (1,-1) has 0 X's and 1 O (worth -1) The other windows of 3 tiles are 'dead' as they have both X and O (worth 0) So the static evaluation returned 9 = (10 + 1 - 1 - 1) Correctly showing the advantage to X in this board position.

5c. (1) It ignores whose turn it is. The 9 above is for a position where O is about to block, but a leaf with the same two-in-a-row and X to move is a win for X next turn and scores the same, so at a leaf it can badly misjudge a threat. (2) Overlapping windows count the same marks again and again, and open and closed lines are valued the same. In five-in-a-row, three X's in the middle of an open row make several overlapping windows, which can outscore a single four (a window worth 1000 equals ten three-windows at 100 each) even though the four is a real immediate threat. It also can't see double threats (forks) directly, only by searching deeper.

Describe points of difficulty you encountered and how you resolved

out to be, and what the fix was.  Examples of issues students

  - Returning the original state instead of a deep copy
  - Alpha-beta cutoff conditions inverted (pruning too aggressively

(1) Bug: make_move could end up with no move. The symptom was a None move coming back at the start of a game. The root cause was that best_val started at -inf / +inf and a child only replaced it if its score was strictly better, so if every child scored +/-inf (or NaN) best_move was never set. The fix was to always take the first child (best_move is None or ...) and only replace it with a strictly better one after that.

(2) Bug: games that never ended. The symptom was a game that kept running. The cause was in the loop in make_move, which had no good stopping rules. I fixed it by breaking out when a forced win or loss has been found (deeper search can't change it), when the depth reaches max_ply in demo mode, when the depth reaches the number of blank squares (the whole tree has been searched), and when the time budget has gone.

(3) Difficulty: the comments suggested building the successor states in make_move, but that duplicated the work and made it hard to share the alpha-beta window between the root's children. I moved all of the successor generation into minimax so make_move makes one root call.

(4) Difficulty with the transposition table: a table hit returns a value but no state, but make_move needs the state of the best move. So the root is never answered from the table. I also had to clear the table when the special static evaluator changes, since the stored values are not comparable.

Zobrist hashing with a transposition table (and best-move ordering from the table): Each (square, piece) pair gets a random 64-bit key from a fixed seed (415) and a position's hash is the XOR of the keys of its pieces, with one extra key XORed in when it is O's move so that the same board with a different side to move hashes differently. The table maps hash to (depth searched, value, flag, best move). The flag is EXACT, LOWER or UPPER depending on whether the value fell inside the alpha-beta window or a cutoff happened. An entry is only reused if it was searched at least as deep as needed, a shallower search never overwrites a deeper one, and a stored best move is tried first to improve pruning. Measurement (tic-tac-toe, empty board, alpha-beta on, depth 5): without the table 1985 static evals and 539 cutoffs; with the table 1070 static evals (46% fewer) and 323 cutoffs. The table got 496 entries written and 207 hits, of which 183 were reused directly for a value or a cutoff and 24 were used only to order the moves. Both chose (1,1). I learned that the bound flags are the hard part, and that a table hit is only safe if the depth is enough.

Iterative deepening with a time budget
make_move searches depth 1, 2, 3... and keeps the last depth that finished. The deadline is 0.8 of the time limit (at most 2.5 s in demo mode), and minimax checks the clock once every 256 nodes and raises OutOfTime if it has passed. In competition mode max_ply is the minimum and the clock decides how deep to go. It stops early if a forced win or loss is found or the whole game tree has been searched. I learned that depth 1 always has to finish so there is always a move to return.
